# 第二阶段实施与权限基线

日期：2026-10-20；站内提醒及任务闭环与节点核销联动按用户2026-10-22要求更新。用户明确要求开始完成第二阶段，并在本聊天回复“采用上述权限基线”。

## 已确认权限

- 公共动作模板、提醒规则、企业日历由系统管理员编制；另一名具有有效项目 admin/reviewer 角色的人员独立批准。所有编制人均不可批准自己的配置。公共配置供授权用户读取和复用，不由任意项目编辑人员更改。
- 已批准提醒规则到达触发日后自动站内投递，无需逐条提交、审核或发布。提醒、通知、待办及投递记录在同一项目事务中保存，失败整体回滚，重复扫描不重复投递。对外正式函件仍需审批；当前外部渠道继续关闭。升级前遗留草稿保留原编辑、独立审核和人工发布接口，不自动批量补发。
- 项目 admin/editor 分派任务；指定执行人反馈，另一名项目 admin/reviewer 独立核实。延续第一阶段的只读语义，执行人须有项目编辑权限；reviewer如兼任执行人员，需要显式授予editor，仍不能核实自己的反馈。
- 项目角色撤销/账号停用即时校验；系统管理员编制公共配置不隐含未授权项目的业务访问权。

## 由配置决定的业务内容

1. 模板的适用节点类型、可选项目类型、动作、材料、责任部门与核实依据均由用户编制；未经批准不匹配/绑定。历史版本不可覆盖，只有草稿可编辑。
2. 每个提醒规则明确提前天数、自然日/工作日、接收角色、日历版本与追补窗口。默认追补0天表示只在触发当日生成；没有自动无限补发。当前每一计划快照/规则版本/接收人发送一轮站内提醒；重复运行返回跳过原因。
3. 工作日历对覆盖区间的每一天显式给出工作/非工作标记，且独立批准。预填周末只是编制草稿的辅助操作；没有真实企业节假日资料，不提供默认批准日历。倒推不计计划日，从前一天开始计数；自然日则直接减天数。UI可试算，但规则未批准不进入正式扫描。
4. 扫描仅基于当前生效计划、未取消节点和批准配置；当前已核实完成的节点跳过。模拟日期用于开发/测试，不重放任意日期的历史计划。生产生成接口仅接受当前业务日期。
5. 通知正文由保存的结构化事实与动作确定性整理，标记 `deterministic_template`，不调用模型，不冒充AI。样本属性进入事实快照；不生成实际完成、合同满足或实际收付款结论。
6. 计划采用基准版本与节点增量：新建版本不复制节点，编辑时仅保存改动节点及其动作快照，查询时还原完整计划。新版生效只作废被替换/移出节点的待发稿及旧任务；未改动节点沿用原动作和提醒引用，不重复生成。受影响的未开始任务取消，进行中/待核实任务保留并标记来源需复核，禁止继续核实；编辑可明确取消后使用新版本任务。从旧基准恢复曾失效节点时建立新的任务引用，不复活已取消历史。已发送通知及核实完成任务历史保留。界面可仅看本版变更，展示新旧日期差及原因；旧库全量快照兼容保留。
7. 模板、规则、日历停用/替换也作废其待发稿及未开始任务，开始执行的记录标需复核。任务以动作关联和规则版本防重，不为每个通知接收人复制任务；规则新版本可创建新任务，已取消旧任务不会阻止新任务生成。
8. 反馈接受完成相应准备动作，并更新任务详情中的节点动作核实进度。当前生效节点的全部标准动作均已生成任务并核实完成后，符合条件的审核人可在原任务抽屉确认节点本身实际完成、填写实际日期，一键沿用任务凭证生成已核实节点实际记录，无需重复申请和审核。任何相关任务反馈提交人不得自行核销；旧计划、取消/缺失/未核实任务、配置或来源失效、已有待审节点实际记录均阻止核销。核销使用项目事务锁、节点版本及现有当前实际记录唯一约束，重复请求不重复记账；历史事实保留。退回/异议保留原反馈与核实事件，执行人可提交新反馈。准备动作不自动证明船体完工或款项到账，不生成财务收付款记录。
9. 外部邮件/短信/企业消息未授权，发送适配层明确拒绝这些渠道。站内消息按批准规则自动投递并留投递记录，接收人可标记已读；不把“已站内发布”表述为外部平台已送达。

前述权限为用户明确确认。天数、日历、模板内容和正式接收角色仍需企业在配置中逐条批准；不得将代码默认值或模拟Excel草案当作企业正式规则。原始计划书与需求说明书原件仍未提供。
