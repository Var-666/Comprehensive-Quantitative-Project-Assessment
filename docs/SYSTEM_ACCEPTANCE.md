# V0.4.0 综合联调记录

记录日期：2026-10-20。范围为现有系统的技术联调和模拟业务验收，不代表企业正式业务验收，不增加新的业务判断口径。

## 本次修复

- 旧环境配置迁移和运行时复用现有凭据、模型字段校验；拒绝将误填到地址或模型编号中的 Key 公开，失败不留下部分配置。
- 结构化请求按事实所属区段限制可引用 ID；没有授权财务事实时不提供财务建议代码。明确要求建议代码不重复，后端继续拒绝遗漏、重复、跨区段引用、额外文字及截断结果，不自动重试或降级。
- 系统设置区分“列表读取成功”和“基础调用通过”，说明短调用验证不能替代结构化报告验证。
- AI 报告按钮使用原型对应的 18px SVG；量化评估详情移除错误复用的导航图标。

## 真实模型验证的边界

两个真实运行均只读本机模型配置，将加密凭据和模型选择复制到隔离模拟库；不复制业务表。只向 CMHK 发送 `id`、`section`、`kind`，不发送正文、项目名称、日期和金额。TLS 验证开启，环境代理及自动跳转关闭；每次业务请求显式允许外送。配置摘要核对确认本机模型配置未被验收修改。

默认 `CM-Pub-DeepSeek-V4-Flash` 的 4 次调用约 1.18–1.45 秒。独立通知场景 `CM-Pub-GLM-5.1-PD` 的通知、工作安排调用分别约 21.45、30.75 秒，隔离验收超时为 60 秒；其余两次使用默认 DeepSeek。本机原超时仍为 20 秒，没有自动改为 60 秒。选择 GLM 前需通过已有管理员设置评估超时。

初次 GLM 联调曾超时；一次 DeepSeek 返回重复建议代码，被后端以无效模型输出拒绝，没有保存成功报告。之后收紧请求 Schema 和提示，最终两个场景运行通过。通过仅表示记录中的样本，不保证后续输出全部合规，也不证明发现的全部模型适用于报告。

默认 pytest 使用明确 Mock 且禁止联网。真实运行必须显式设置 `RUN_REAL_LLM_ACCEPTANCE=1`，使用已启用、已验证的现有配置，命令见 README。不要把 `TEST_DATABASE_URL` 指向业务数据库。

## 环境问题与剩余事项

- 初次 PostgreSQL 验证遇到 Docker 未启动；启动后完整重跑通过。新增布局用例初次存在登录等待和页面标题断言错误，修正测试后通过。
- 企业真实业务人员验收、正式部署网络与权限审批、SSO、附件存储及企业财务对账未在本次执行；外部消息发送保持既定适配层范围。
- 最初列出的计划书及需求说明原件未全部提供；本轮不补造业务规则，沿用仓库已有设计、模拟 Excel、可访问原型和已确认口径。
- 本次没有新增数据表、数据库迁移、主菜单或评价口径。模型仍可能超时或返回无效输出，系统明确报错，管理员或用户决定后续操作。

机器汇总见 `system-acceptance-results.json`。真实调用记录仅含模型编号、状态、时长和步骤，不包含 Key、请求正文或生成正文。
